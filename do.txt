✨ OPTIMIZE — design proposal (not implemented)
=================================================

What it does
------------
Converts the pages of manga, comics or Cosplay sets to AVIF — typically 50–80% smaller than JPEG at the
same visual quality, and far smaller than PNG. Every current browser (Chrome, Edge, Firefox, Safari) shows
AVIF directly, so unlike JPEG XL / HEIC it needs no transcoding when you read — it would also be the natural
target for those formats.


1. WHERE THE BUTTON LIVES — four placement options
---------------------------------------------------

A. Per item, in the ⋯ menu  (the core — recommended)

     ⋯  Edit details…
        Move to collection ›
        ✨ Optimize…            <- series / collection / set / multi-select
        Add to Favourites ›

   - Works for: single series, Cosplay collections, single sets, and multi-select ("✨ Optimize 12 series").
   - Pro: it's where you already manage things; you choose exactly what gets converted.
   - Con: a whole library means a lot of clicks (option B solves that).

B. Library level, in Edit library  (the bulk path)

     Edit library > Storage
        312 series · 48.2 GB   (AVIF-ready: 41 GB could be saved)
        [ ✨ Optimize whole library… ]
        [ ] Auto-optimize new uploads

   - Pro: set it once and forget it; shows the payoff before you commit.
   - Con: a large job — needs a solid background queue (see 4).

C. At upload time, in the drop / upload dialog

     Adding 42 files…   [ ✨ Optimize to AVIF ] [ Keep as is ]

   - Pro: files never land on disk in the big format.
   - Con: uploads finish much later (encoding is slow). Better: upload as-is, queue the optimizing afterwards.

D. A "✨ Storage" page in the sidebar, under Favourites
   - Dashboard: total size per library, biggest series, "not optimized yet", savings so far,
     one-click "Optimize the 20 biggest".
   - Pro: the most satisfying view — you see the gigabytes come back.
   - Con: more UI to build; a later phase.

Badges that go with every placement:
   - an AVIF frosted pill (like RAW / JPEG XL) on optimized series
   - a small ✨ "could save ~X GB" hint on large unoptimized ones — only in D / Edit library, never on every card


2. THE OPTIMIZE DIALOG — three designs
---------------------------------------

Design 1 — "Presets" (simple, recommended)

     ✨ Optimize "Someone's Collection"            12 sets · 1,840 photos · 9.6 GB

        (•) Visually lossless   ~4.1 GB  (-57%)   for archiving / RAW sources
        ( ) Balanced            ~2.3 GB  (-76%)   reading on any screen
        ( ) Compact             ~1.2 GB  (-88%)   phones, slow connections

        [x] Shrink huge photos to 4000 px on the long edge   (6000×4000 -> 4000×2667)
        [x] Keep originals for 14 days   (in /config/originals, undo anytime)

        [ Compare a sample page ]                 [ Cancel ]  [ ✨ Optimize ]

   Size estimates come from encoding 3–5 sample pages first (seconds) and scaling up.

Design 2 — "Before / after" (visual)
   - The same dialog plus a split-slider comparison of one real page at full zoom.
   - Switching presets re-encodes that page live.
   - Best for trust: you SEE that "Balanced" looks identical before committing 9 GB.

Design 3 — "Advanced" (a collapsed section under Design 1)
   - Quality slider (AVIF 0–100)
   - Encoder speed (slower = smaller)
   - Colour: auto / 4:4:4 / 4:2:0 (4:4:4 keeps black-and-white line art and red text crisp)
   - Grayscale detection on/off
   - Max size

Suggestion: Design 1 + the Design 2 compare button + the Design 3 section folded away —
simple by default, inspectable on demand.


3. SMART DEFAULTS PER LIBRARY TYPE
----------------------------------

                     Manga / comics                                 Cosplay
   Typical source    JPEG/PNG scans, line art                       6000 px camera JPEGs, HEIC
   Colour            auto-grayscale for B&W pages (big win);        4:2:0 (photos)
                     4:4:4 for colour pages so red/black lines
                     don't bleed
   Resize            off by default (scans are rarely huge)         ON, 4000 px long edge (biggest saving)
   Preset            Balanced                                       Visually lossless
   Videos            —                                              untouched, always
   Animated GIF      untouched (AVIF animation support is patchier) same

Format-specific rules
   - PNG/BMP/TIFF (RAW) series: warn that the RAW pill goes away. Offer "Lossless AVIF", but only where it
     actually comes out smaller (often not the case for line art).
   - JPEG XL / HEIC series: converting removes the "Transcoding…" wait forever. Suggest it in the reader:
     "This set is HEIC — ✨ Optimize to AVIF so it opens instantly?"
   - Per page: if the AVIF version is BIGGER than the original (tiny or already-compressed pages),
     that page keeps its original.


4. HOW IT RUNS — three engine options
-------------------------------------

Option 1 — a background job queue  (recommended)
   - One worker inside the container; a queue that survives restarts (/config/jobs.json).
   - Encoding: a few pages in parallel, at low priority so reading stays smooth.
   - UI: a Jobs panel like the upload panel — minimisable, with Pause / Resume / Cancel.
     e.g. "Optimizing 3 of 12 sets · 412/1840 pages · ~18 min left · saved 2.1 GB"
   - Optional "Only between 01:00 and 07:00" setting for big libraries.

Option 2 — a separate optimizer container
   - The same queue, but encoding runs in a second container (compose service) you can limit in CPU / RAM,
     or run on another machine.
   - Pro: the reader is never slowed down.  Con: more setup — worth it only for very large libraries.

Option 3 — in the browser
   - The browser encodes (like the current .cbz packing).
   - Pro: no server CPU.  Con: slow, the tab has to stay open, phones would choke.
     Not recommended beyond small upload-time use.

Safety, whichever engine
   1. Write the new .cbz (or photos) to a temp file -> check every page decodes and the page count matches
      -> swap it in atomically.
   2. The file name stays the same, so book IDs, reading progress, favourites and the chosen cover (page
      index) all survive. metadata.json / ComicInfo are carried over.
   3. Originals go to /config/originals for N days, with Undo in the ⋯ menu; the cache clean-up deletes them
      after that. Optionally "Replace without keeping" for people short on space.
   4. Photo-set folders (not archives): convert files in place (.jpg -> .avif), same backup.
   5. A locked file (open on Windows) is skipped with a note and retried at the end — never half-done.


5. SUGGESTED ROLLOUT
--------------------
   Phase 1: ⋯ menu + dialog (Design 1 + compare) + job queue with Jobs panel + keep originals / Undo
            + AVIF pill.
   Phase 2: library-level "Optimize all" and auto-optimize new uploads, plus the "HEIC/JXL -> AVIF"
            suggestion in the reader.
   Phase 3: the ✨ Storage page and night-only scheduling.


DECISIONS TO MAKE
-----------------
   1. Keep originals by default? Yes for 14 days / yes forever (no space saved until cleared) / replace now?
   2. Resizing huge Cosplay photos: on by default, or opt-in only? (Biggest saving, but the only step that
      throws away pixels.)
   3. Which placements in phase 1: just the ⋯ menu, or also the library-level button?
   4. Engine: a worker inside the reader container (simple) or a separate optimizer container
      (never slows reading)?
